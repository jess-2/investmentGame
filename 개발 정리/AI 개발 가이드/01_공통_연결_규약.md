# 현재 계약: prototype-v4 / rules-v4-daily-open (2026-11-08)

v4 개정: `BUY_INFORMATION_WINDOW`는 `companyId`, `startDay`, **`endDay`**를 받는다. 개인 구매는 1~30일 안의 임의 연속 구간이며 신규 날짜당 1코인이다. 공개 선택만 연속 5일이다. 두 날짜를 JSON 정수로 검증하고 요청 지문에 함께 넣는다. `PlayerView.entryAtOpen`과 창/결과의 **`dailyOpenBps`**를 추가했다. 시가 배열과 종가 배열은 구매 범위 길이와 같고 다른 날짜의 봉을 공개하지 않는다. 정보상 무료권 수치는 v4에서 무료로 남은 **날짜 수**다. 상세는 [v4 개정](../참고사항/DAILY_INFO_MOUSE_TRADING.md)을 따른다. 아래 v3 및 고정 v2 형식은 개정 이력이다.

아래 v2 fixture 계약은 고정 비교용으로 보존한다. 일반 방은 다음 필드를 사용하는 v3이며 `bundleIndex`를 시작일로 재해석하지 않는다.

| 명령 | payload | 동작 |
| --- | --- | --- |
| `REVEAL_INFORMATION_WINDOW` | `companyId`, `startDay` | INFO 공용 차례의 본인만 5일 공개. 전원 개인뷰 갱신 |
| `BUY_INFORMATION_WINDOW` | `companyId`, `startDay` | 공용 공개 종료 후 개인 구매. 구매자는 해당 창만 수신 |
| `USE_INFORMATION_ITEM` | `itemId`, `companyId`, `startDay`, `targetPlayerId` | BLACKBOX는 기업/시작일, STEAL·INFORMATION_STEAL·DISTORT는 대상 플레이어 사용 |

시작일은 JSON 정수 1~26, 길이는 5로 고정한다. 서버 신원·요청 ID·턴·단계·기한·차례 검사를 통과한 요청만 처리한다. 응답은 기존 `<명령>_RESULT` 형식이며 창 결과는 `recordId`, `source`, `startDay`, `dailyChangesBps`, `paidCoins`, `remainingCoins`를 담는다.

- `PUBLIC_STATE`: `windowInformation`, `publicSelectionActive`, `publicSelectionIndex`, `publicSelectionPlayerId`, `publicSelectionDeadlineAtServerSeconds`, `publicInformation[]` 추가. 공개 기록은 선택자·기업·시작일·자동 여부만 포함한다.
- `PLAYER_VIEW.companies[].visibleWindows[]`: `recordId`, `source`, `startDay`, `paidCoins`, 허용된 5일 값만 포함한다. 같은 날짜의 여러 근거를 유지한다. 다른 플레이어의 개인 구매 기록은 전달하지 않는다.
- 전체 INFO 기한은 `phaseEndsAtServerSeconds`이고 공용 차례 중 타이머는 `publicSelectionDeadlineAtServerSeconds`를 표시한다. 공용 공개가 끝나도 INFO 기한은 늘리지 않는다.
- v2 `BUY_INFORMATION`은 일반 v3 방에서 거절한다. 고정 fixture의 `visibleBundles` 계약은 변경하지 않는다. UI/BOT은 v3 방에서 날짜 마스크와 새 명령을 사용한다.
- 재접속은 현재 공개 기록·차례·기한과 본인의 열람 창을 복구한다. 시드·패턴 유형·제어점·숨은 날짜 값을 전송하지 않는다.

# 공통 상태·기능 연결 규약

2026-11-02 이후: Shared는 이미 구현되어 있다. 아래 최초 제안/fixture 설명을 새 DTO 생성 지시로 해석하지 않는다. [04 현황](./04_현재_구현_현황.md)과 [05 계획](./05_다음_구현_계획.md)을 먼저 읽는다.

## 다음 개선의 연결 경계

- 차주 범위는10턴·3/6/9턴 입찰·전광판·아이템·고유능력까지 확대됐다. 현재 없는 AUCTION/능력 선택/상점·사용 명령과 결과·개인 인벤토리/능력 상태·공개 효과 이벤트는 A/B/C/D가 Shared 단일 계약으로 정의한다. 현재 코드에 이미 있는 API로 간주하지 않는다.
- A는 턴/단계/요청 신원과 수신시각, B는 시장/자산/비용/정산, C는 입찰/아이템/능력/코인 원장, D는 의도 입력/표시를 맡는다. B 비용 확정과 C 지급/소모는 사전검증·한 방 직렬 처리·재전송 키로 부분 적용을 방지한다.
- 최종 승자 집계에는 B 자산·성과, C 최종 코인, A 시작 추첨순번을 같은 종료 스냅샷으로 조합한다. 공개 전광판에 타인 주문·구매값·비밀 입찰 원문을 추가하지 않는다.

- INFO90초는 A의 서버 설정과 기존 마감 DTO를 사용한다. 아래50초/120초/74초/97초는 `basic-turn-v2` 회귀 기준이다.
- 막대·마우스 날짜·구간 취소는 D 표시/초안 변경이며 기존 `SUBMIT_INVESTMENT`와 B 최종 검증을 유지한다.
- 자리 후보 선택/취소 권장안은 로컬 상태만 바꾸고 확정에서 `SELECT_COMPANY`를 보낸다. 현재 서버 확정 선택 취소 명령은 없다.
- 자리 강조는 공개 `remainingSeats`+본인 `selectedCompanies`만 사용한다. 타인 이름별 투자 목록을 추가 공개하지 않는다.
- BOT은 개인뷰/공개 상태와 기존 명령만 사용한다. C 시장 조회 인터페이스나 B 원본을 전략에 제공하지 않는다.
- 난이도·진행 설정 API는 아직 없다. 첫 구현은 방장 내부 주입으로 가능하고, 전송을 추가하면 A가 Shared/복사/코덱/검사/예시를 함께 갱신한다.

계약 기준: `prototype-v2`, 게임규칙 `rules-v2`, fixture 파일형식 `schemaVersion: "1.0"`. [규칙 확정 기록](./02_결정_사항.md)을 적용한다. 아래 서비스명은 논리적 경계이며 실제 C# 선언은 A가 공통 PR로 제안하고 B·C·D가 확인한 Shared 하나를 사용한다.

## 상태는 한 담당만 변경한다

| 상태 | 최종 변경 담당 | 다른 기능에서 쓰는 방법 |
|---|---|---|
| 접속자·방장·준비 | A | 공개 참가자 스냅샷 조회 |
| 현재 턴·진행 단계·선택 인덱스·마감 시각 | A | 규칙 호출에 읽기 전용 문맥 전달 |
| 기업 전체 주가·공개 묶음 위치 | B | 시장 생성·정보 묶음 조회. C는 무료 묶음을 재추첨하지 않음 |
| 참가자별 선택 기업·기업 정원 | B | A가 선택 검증/확정을 요청하고 성공 결과로 차례를 전진 |
| 참가자별 투자 주문·자산·정산·순위 | B | A가 주문 잠금과 정산 시점을 지시 |
| 코인·지급 원장·구매 원장 | C | A가 턴 시작을 호출하고 C가 멱등 지급 |
| 플레이어별 정보 열람 데이터 | C | B 원본과 본인 원장에서 필터링하여 A가 대상에게 전달 |
| 화면 선택·구매 대기·클라이언트 캐시 | D | 서버 결과로 갱신. 실제 자산·코인을 직접 확정하지 않음 |

B와 C는 GameObject/UI나 RPC 연결에 의존하지 않는 규칙 계층으로 만든다. A가 규칙 호출을 조정하고 D는 클라이언트 서비스만 사용한다. 공통 상태 객체를 쓰더라도 변경 권한은 위 표대로 한정한다. 복사본을 각각 수정한 뒤 서로 덮어쓰지 않는다.

### 게임 UI 대기실 연결 (2026-11-02)

- `DevTabletUI` 씬의 `DevTabletBootstrap`이 `NetworkSession`을 생성한다. 방장은 실제 B/C를 공급하고, 방장·참가자·BOT 모두 TCP 클라이언트와 같은 Command 경로를 사용한다.
- 공개 참가자 DTO `Player`에 `isBot: bool`을 추가했다. 필드가 없는 기존 데이터의 기본값은 `false`이며, UI 복사본에도 보존한다. 이름으로 BOT 여부를 판단하지 않는다.
- BOT 등록·제거와 연결이 끊긴 대기실 자리 회수는 방장 프로세스의 관리 기능이다. 새 네트워크 명령을 만들지 않았고 참가자는 이 기능을 호출할 수 없다. 게임 시작 후에는 명단을 바꾸지 않는다.
- 대기실에서 방장이 빈자리를 BOT으로 채우면 연결이 끊긴 참가자의 자리 예약·재접속 토큰을 먼저 폐기한다. 채우기를 누르기 전에는 기존 30초 재접속 정책을 유지한다. BOT을 내보낸 자리는 사람이 다시 사용할 수 있으며 이전 참가자의 요청 캐시를 재사용하지 않는다.
- 사용 절차와 검증 범위는 [게임 UI 멀티플레이 연결](./D/멀티플레이_UI_연결.md)을 참고한다.

기존 D 개인 fixture의 `ownInvestments`는 INFO 단계라 빈 배열이다. 실제 투자 단계에서는 B가 관리하는 본인 주문을 읽어 C 또는 공통 프로젝터가 조합한다. C가 자산·주문을 다시 계산하지 않는다.

## 처리 순서와 원자성

```text
D: 요청 생성
→ A: 접속 신원·턴·단계·재전송 검사
→ B 또는 C: 규칙 검증과 상태 확정
→ A: 성공 시 진행 갱신, 결과를 개인/공개 범위에 맞게 전송
→ D: 현재 요청·턴에 맞는 결과만 화면에 반영
```

- 한 방의 상태 변경 요청은 순서대로 처리한다. 코인 1개 상태에서 두 구매가 모두 성공하거나 남은 자리 1개에 두 요청이 모두 성공하지 않게 한다.
- A의 공통 검사를 통과해도 B·C는 필수 도메인 조건을 검증한다. 어느 계층에서 실행해도 같은 실패 코드와 무변경 상태를 보장한다.
- 코인 차감과 구매 원장 추가는 함께 성공한다. 원본 조회 실패 시 차감만 남기지 않는다.
- 차례는 B가 선택 성공을 반환한 뒤에만 A가 한 칸 전진시킨다. 실패 요청은 차례·자리 모두 유지한다.
- 주문 잠금·정산 적용·코인 지급은 턴을 키로 중복 적용을 막는다. fixture 재로딩은 실제 게임에서 상태를 초기화하는 명령이 아니다.

## 고정 요청·응답

실제 예시는 [exchange_examples.json](../임시%20데이터%20및%20검증용/exchange_examples.json)에 있다. 파일 외곽의 `senderPlayerId`, `recipientPlayerId`, `broadcast`는 시뮬레이션 라우팅 메타데이터다. 네트워크 본문은 안쪽 `request`와 `response`다.

```json
{
  "type": "BUY_INFORMATION",
  "requestId": "info-001",
  "turn": 1,
  "payload": {"companyId": "AI", "bundleIndex": 1}
}
```

```json
{
  "type": "BUY_INFORMATION_RESULT",
  "requestId": "info-001",
  "turn": 1,
  "success": true,
  "errorCode": "",
  "payload": {
    "remainingCoins": 2,
    "companyId": "AI",
    "bundleIndex": 1,
    "startDay": 6,
    "dailyChangesBps": [-1500, -2000, -2500, -3000, -4000]
  }
}
```

- C가 성공 payload를 만들고 A가 P1에게만 보낸다. D는 받은 묶음을 `source: "PURCHASED"`로 본인 캐시에 추가한다.
- `D_P1_after_purchase.json`은 전체 개인 상태이고 위 응답은 변경된 일부 값이다. 응답을 전체 상태로 오해하여 다른 기업의 공개 정보를 삭제하지 않는다.
- 실패 사례의 `expected.remainingCoins`나 `purchasedBundleCount`는 참조 검증 결과다. 모두 실제 통신 payload에 포함한다는 뜻이 아니다. 실패 응답 DTO는 A·C·D가 같은 선언을 사용하고 구매 정보는 포함하지 않는다.
- `SELECT_COMPANY` 요청과 공개 갱신은 `A_selection_replay.json`, `SUBMIT_INVESTMENT`는 `exchange_examples.json`을 기준으로 한다.
- 선택 fixture의 `expectedPrivateResult`는 payload에 해당하는 부분 결과다. 완전한 통신 envelope가 아니다. A가 공통 결과 envelope로 감싸는 형식은 Shared PR에서 하나로 정한다.
- fixture의 `schemaVersion`은 파일 형식 버전이다. 접속 시 프로토콜 호환성 검사가 구현되었다는 뜻이 아니다. 이를 추가하면 A가 제안하고 전체 예시·코드를 함께 변경한다.

## 기존 오류 코드

| 호출 | 코드 |

기존 사례의 검사 우선순위는 각 기대 결과와 참조 구현에 맞춘다. `MISSING_INTERVAL`, `REQUEST_ID_CONFLICT`, `RATE_LIMITED`도 공통 코드로 정의한다. 빈 구간·소수 날짜 등 추가 주문 사례를 포함한 34건이 있어도 미접속자·실제 동시요청·네트워크 장애·전체 효과가 모두 검증된 것은 아니다.

## 공개 범위

| 데이터 | 수신 대상 |
|---|---|
| 참가자·단계·현재 선택자·기업별 남은 자리 | 전체 |
| 기업별 무료2묶음 | 전원에게 동일한 내용 |
| 구매 묶음·코인 잔액·본인 주문 | 해당 본인만 |
| 전체 구매 원장·전체 주문·미공개 시장 원본 | 서버 내부 |
| 성과·누적·순위·추이 | 전체. 타인의 투자 내역 제외 |

시장 공개 이후 연출을 위해 전체 그래프를 보낸다면, 전원의 주문이 잠긴 상태에서 A가 명시적으로 공개 모드를 바꾼다. 공개 전 개인뷰 처리와 섞어 비공개 값이 먼저 전달되지 않게 한다.

## 통합 의존 순서

1. A가 Shared DTO·서비스 경계·버전 정보를 정리한다. B/C/D의 사용 측 리뷰 뒤 먼저 병합한다.
2. B는 고정 시장·검증·정산, C는 정보 구매·개인뷰, D는 같은 서비스의 Mock으로 병렬 작업한다.
3. Mock을 B/C의 실제 로컬 호출로 바꾸고 동일 고정 입력에서 결과가 일치하는지 확인한다.
4. A가 네트워크를 연결한다. D의 입출력은 유지하고 4개 창·실제 PC 4대에서 수신 대상을 확인한다.
5. 고정1턴이 통과한 뒤 복수 턴·시간 제한·난수 시장으로 확장한다. Mock이 남은 모드를 실제 연결 완료라고 부르지 않는다.

## 사례 실행 기록

각 담당의 `통과기준.json`에는 원본34건에서 추출한 `referenceCases`와 실제 구현에 적용할 `integrationChecks`가 있다. 기대값과 실측값은 별도로 기록하고 기대값 파일 자체에 PASS를 쓰지 않는다.

## rules-v2 추가 연결 기준

- 날짜는 정수 일별, 보유기간은5~10일. B가 검증하고 D가 같은 규칙의 날짜 입력을 제공한다. 무료/구매 정보의5일 묶음과 날짜 선택 격자를 혼동하지 않는다.
- INFO는 일반50초/입찰턴35초, 선택은 성공마다 최대4초, 주문23초다. 서버 수신시각이 마감 이상인 새 요청은 거절하고, 기존 처리의 재전송은 캐시만 반환한다.
- A가 미제출 자동행동을 서버 명령으로 만들고 B/C 규칙을 동일하게 호출한다. 선택/주문의 기본값과 효과 순서는02에 있다.
- B가 비용 차감 후 투자금 I와 자산0/재기지원 상태를 관리하고 C는 상점/입찰 확정 비용을 B의 자산원장에 한 번 반영하도록 A와 연결한다. C가 별도 자산 잔액을 복제하지 않는다.
- 기존 기본 fixture는 효과·비용 없음, 능력NONE이므로 수동 정산값은 유지된다. 전체 효과가 확정되어도 현재 기본 사례가 이를 자동 검증하지는 않는다.
- 선택 단계의 `phaseEndsAtServerSeconds`는 전체 선택 단계 상한, `selectionDeadlineAtServerSeconds`는 현재 차례의4초 마감이다. 다른 단계에서는 후자를0으로 둔다. 선택 replay의 `requestReceivedAtServerSeconds`는 서버 시각 주입용 테스트 메타데이터이며 클라이언트가 주장하는 수신시각이 아니다.
- replay는 INFO50초 뒤 각 선택에3초씩 사용하여74초에 투자를 시작하고97초에 주문 마감하는 조기 진행 예시다. 120초는 상한이므로 다음 단계의 마감을 무조건105초로 고정하지 않는다.
