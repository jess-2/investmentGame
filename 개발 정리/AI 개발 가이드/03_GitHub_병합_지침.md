# 4인 Unity 개발을 위한 GitHub 병합 지침

## 1. 이 문서의 적용 범위

이 문서는 A·B·C·D가 각자의 AI 모델을 이용해 구현한 기능을 하나의 게임으로 연결하기 위한 팀 운영안이다. 현재 작업공간에 Unity 프로젝트가 만들어져 있다는 뜻은 아니다. 아래 `Assets/...`, `Packages/...`, `ProjectSettings/...` 경로는 **앞으로 만들 Unity 프로젝트 내부의 예시 경로**이며, 실제 프로젝트 위치에 맞춰 사용한다.

게임 규칙과 전달 데이터는 [공통 맥락](./00_공통_맥락.md), [공통 연결 규약](./01_공통_연결_규약.md), [규칙 확정 기록](./02_결정_사항.md)을 기준으로 한다. GitHub에 코드가 합쳐진 것과 실제 게임에서 연결된 것은 따로 확인한다.

## 2. 시작할 때 함께 정할 것

| 항목 | 팀 운영안 |
|---|---|
| 개발 통합 브랜치 | `dev`. 모든 개발자는 기능 브랜치에서 완료한 작업을 `dev` 대상 PR로 제출한다. |
| 안정 버전 브랜치 | `main`. `dev`에서 통합 검증을 마친 버전을 관리자가 PR로 반영한다. |
| 작업 브랜치 | 최신 `dev`에서 `feat/23-info-purchase`처럼 기능 하나마다 생성한다. |
| 작업 단위 | GitHub Issue 하나에 담당자·완료 조건·선행 작업을 적는다. |
| 리뷰 | 작성자 외 팀원 1명 이상이 확인한다. 공통 계약 변경은 영향을 받는 담당자가 확인한다. |
| 병합 담당 | PR마다 정한다. 공통 Scene을 조정하는 사람도 시점별로 정한다. |
| 개발 환경 | Unity 에디터의 정확한 버전과 패키지 버전을 통일한다. |
| 게임 규칙 변경 | rules-v2 및 이후 변경 합의를 문서·데이터·구현에 함께 반영한다. |

4명 모두 서버 규칙을 구현할 수 있지만, 각 상태의 최종 변경 책임은 하나로 정한다. 예를 들어 A는 차례·단계를 관리하고, B는 투자 선택의 정원·주문을 검증하며, C는 코인·정보 열람 상태를 변경한다. 실제 책임 구분은 공통 연결 규약에 맞춘다. A와 B가 같은 선택 상태를 각각 보유해 따로 갱신하는 방식은 피한다.

가능하면 저장소 설정에서 `dev`와 `main`에 PR 리뷰와 필수 검사 통과를 요구한다. 보호 규칙의 사용 가능 범위는 공개·비공개 저장소와 GitHub 요금제에 따라 다르다. 설정을 사용할 수 없다면 같은 절차를 팀 규칙으로 지킨다. [GitHub 공식 보호 브랜치 안내](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches)

## 3. AI에 작업을 맡길 때마다 최신 파일을 읽힌다

예전에 AI에게 전달했던 파일은 이후 바뀌었을 수 있다. 작업을 시작할 때 다음 자료를 다시 제공하거나 현재 저장소에서 읽도록 한다.

1. 공통 맥락과 공통 연결 규약.
2. 본인 역할의 작업지침·임시데이터·통과기준.
3. 실제 저장소의 공통 DTO·서비스 인터페이스.
4. 이번 Issue와 최근에 승인된 규칙 변경.
5. 현재 브랜치, 기준 `dev` 커밋, 이미 존재하는 변경 파일 목록.

AI에게는 다음 작업 원칙을 함께 전달한다.

```text
현재 저장소의 공통 계약과 내 역할 파일을 먼저 읽는다.
이전 대화와 현재 승인된 계약이 다르면 현재 계약을 따른다.
공통 DTO를 내 폴더에 복제하거나 필드·단위를 임의 변경하지 않는다.
다른 담당자의 구현이 필요하면 현재 인터페이스에 맞는 임시 구현을 사용한다.
소유 범위 밖의 변경이 필요하면 영향과 수정안을 먼저 기록한다.
이번 기능에 필요한 파일만 변경하고 기존 사용자·팀원 변경을 보존한다.
실행하지 않은 테스트를 통과했다고 보고하지 않는다.
최신 dev에서 만든 기능 브랜치에서 작업하고, 완료한 기능의 PR 대상(base)은 dev로 지정한다.
커밋·푸시·PR 생성은 이번 요청에서 허용한 범위만 수행하고, PR 병합은 관리자 또는 지정한 병합 담당자에게 맡긴다.
```

AI가 작업을 마치면 사람은 diff를 확인한다. 종료 보고에는 변경 파일, 계약 변경 여부, 사용한 사례와 실제 결과, 아직 임시 구현인 부분을 포함한다. 최신 `dev`에서 공통 계약이 바뀌었다면 작업 중인 AI에도 바뀐 파일을 다시 읽힌다.

## 4. 공통 계약은 먼저 병합한다

공통 계약은 데이터 필드·단위·메시지 이름·에러 코드·서비스 호출 방식이다. 코드를 합칠 때 충돌이 없어도 이 계약이 다르면 동작하지 않는다.

| 변경 대상 | 주 검토자 예시 | 함께 확인할 사람 |
|---|---|---|
| 요청·응답 전달 형식, 진행 단계 | A | 해당 규칙 담당자와 D |
| 투자 주문·정산 결과 | B | A·D, 효과 계산에 영향이 있으면 C |
| 정보 구매·코인·개인 화면 데이터 | C | A·D, 원본 조회가 바뀌면 B |
| UI 서비스 인터페이스 | A·D | 호출되는 규칙 담당자 |
| 규칙·임시 데이터·기대 결과 | 해당 기능 담당자 | 영향을 받는 담당자 |

이 표는 공통 파일을 한 사람만 고칠 수 있다는 뜻이 아니다. 변경한 사람이 영향 범위를 설명하고 필요한 리뷰를 요청한다.

아래 PR은 모두 각 기능 브랜치에서 `dev`를 대상으로 생성한다. 공통 계약도 `dev`에 먼저 병합한다. 정보 구매 기능은 다음 순서로 병합할 수 있다.

```text
PR 1: 공통 구매 요청·응답 DTO와 서비스 인터페이스
          ↓ 병합
PR 2: C의 실제 구매 규칙 + 통과 사례
PR 3: D의 구매 화면 + 같은 인터페이스의 임시 서비스
          ↓ 각각 검증 후 병합
PR 4: A의 실제 통신과 C·D 연결 + 개인 정보 전달 검증
```

PR 2와 PR 3은 PR 1 이후 병렬로 진행할 수 있다. 아직 병합되지 않은 계약에 의존한다면 PR 설명에 선행 PR 번호를 적고 Draft PR로 공유한다. 선행 PR을 병합한 뒤 최신 계약을 반영하고 검증한다. D가 C를 기다리면서 다른 이름의 구매 DTO를 만드는 방식은 사용하지 않는다.

### 데이터 버전과 네트워크 버전은 구분한다

기존 임시 JSON의 `schemaVersion: "1.0"`은 **파일 형식 버전**이다. 특히 기존 `exchange_examples.json`에서는 파일 바깥에 있고 실제 `request`·`response` 안에는 없다. 이 필드만으로 네트워크 버전 검사가 구현됐다고 판단하지 않는다.

네트워크 연결 시 버전 확인을 도입한다면 A가 공통 연결 규약에 교환 방식과 불일치 처리를 제안한다. 채택한 경우 실제 DTO·통신·예시·검증을 같은 변경에 포함한다. 기존 데이터와 다른 필드를 AI가 임의로 추가하지 않는다.

## 5. 매일 작업하는 순서

### ① 최신 dev에서 기능 브랜치 만들기

먼저 `git status`로 현재 작업을 확인한다. 진행 중인 변경이 있으면 현재 작업 브랜치에 적절히 저장하고, 다른 사람의 변경을 지우지 않는다. 아래는 **작업 폴더가 정리되어 있고 `origin`과 `dev`가 있는 경우**의 예시다.

```powershell
git status
git switch dev
git pull --ff-only origin dev
git switch -c feat/23-info-purchase
```

`pull --ff-only`가 실패하면 내 `dev`와 원격의 차이를 확인한다. 기록을 강제로 덮어쓰지 않는다. GitHub Desktop을 사용한다면 최신 `dev` 받기 → 새 브랜치 생성과 같은 의미다.

### ② 구현하고 파일을 골라 커밋하기

Unity에서 파일을 저장한 뒤 변경 목록을 확인한다. `git add .`나 `git add -A`로 전체를 무조건 올리지 않는다. 이번 작업에 필요한 파일만 선택한다.

아래는 Unity 프로젝트 루트에서 실행하는 예시이며 실제 생성한 경로로 바꾼다.

```powershell
git status
git diff
git add -- "Assets/Scripts/Information/InformationService.cs" "Assets/Scripts/Information/InformationService.cs.meta"
git diff --cached
git commit -m "정보 구매 조건 검증과 코인 차감 구현"
git push -u origin feat/23-info-purchase
```

GitHub Desktop에서는 변경 목록에서 이번 파일만 선택하고 diff를 확인한 뒤 Commit·Push한다. 새 에셋은 `.meta`도 포함한다. 실제 구현과 무관한 파일 재정렬·대규모 포맷 변경은 같은 PR에 섞지 않는다.

### ③ PR을 열고 검토받기

기능을 완료한 개발자가 GitHub에서 직접 PR을 생성한다. **대상(base)은 `dev`, 소스(compare)는 본인의 기능 브랜치**로 지정하고 관리자 또는 지정한 리뷰어에게 검토를 요청한다. 리뷰어는 코드를 읽고, 필요한 경우 브랜치를 받아 Unity에서 실행한다. 화면 변경은 이미지나 짧은 실행 결과를 첨부하면 확인하기 쉽다.

PR에는 다음 내용을 적는다.

```markdown
관련 Issue: #23

구현한 동작:
- P1이 AI의 6~10일 정보를 구매하면 코인과 열람 기록을 변경한다.

공통 계약 변경:
- 없음 / 변경 필드와 영향을 받는 A·B·C·D 및 선행 PR

검증:
- 사용한 임시 데이터와 사례 식별자:
- 실제 실행한 C# 검증과 결과:
- Unity 화면 또는 네트워크에서 확인한 결과:
- 아직 실행하지 못한 확인:

Scene·Prefab·.meta 변경:
- 변경 파일과 연결된 오브젝트

임시 구현과 다음 연결:
- 현재 Mock인지 실제 규칙인지
- 다음 연결 담당자와 Issue
```

### ④ 최신 dev를 반영한 결과로 병합하기

다른 PR이 먼저 들어갔다면 내 기능 브랜치에서 최신 `dev`를 합친다. 아래 명령은 **본인 기능 브랜치에 있고 작업이 저장된 상태**에서 사용한다.

```powershell
git fetch origin
git merge origin/dev
```

충돌이 있으면 아래 절차로 해결하고 관련 검증을 다시 한다. 리뷰받은 이후 동작을 바꿨다면 리뷰어에게 알린다. 검토와 검증이 끝나면 관리자 또는 지정한 병합 담당자가 PR을 `dev`에 병합하고, 팀원은 최신 `dev`를 받는다. 타인이 사용하는 브랜치를 합의 없이 rebase하거나 force push하지 않는다.

### ⑤ 통합 검증 후 main에 반영하기

관리자는 `dev`에서 기능 연결과 시연할 흐름을 검증한 뒤 `dev → main` PR을 생성한다. 검토와 검증 후 `main`에 병합해 안정 버전을 남긴다. 팀원의 개별 기능 PR은 계속 `dev`를 대상으로 한다.

## 6. Unity 파일 충돌을 줄이는 규칙

### 버전과 저장 대상을 맞춘다

- `ProjectSettings/ProjectVersion.txt`에 기록된 Unity 버전을 함께 사용한다.
- `Packages/manifest.json`, `Packages/packages-lock.json` 변경은 패키지 담당자와 공유한다. AI가 자기 환경에서 오류를 해결하려고 임의 업데이트하지 않게 한다.
- `Assets`, `Packages`, `ProjectSettings`를 버전 관리하고, 생성 폴더인 `Library`, `Temp`, `Logs` 등은 `.gitignore`에서 제외한다.
- 실제 에셋과 해당 `.meta`를 함께 관리한다. 로컬 사용자 설정과 자격 증명은 올리지 않는다.
- 에디터의 메타 파일 표시와 텍스트 직렬화 설정을 확인한다. 팀이 사용하는 Unity 버전에서 `Visible Meta Files`, `Force Text`에 해당하는 설정을 맞춘다.

### Scene과 Prefab의 편집을 분리한다

예를 들어 공통 Game Scene은 통합 담당자가 조정하고, 정보창·기업 카드·전광판은 별도 Prefab으로 나눠 작업한다. D만 모든 Scene을 수정해야 하는 것은 아니지만, 같은 파일의 동시 수정은 먼저 알린다. 공통 Scene 배치와 이벤트 연결도 Issue의 완료 조건에 포함한다.

```text
Game.unity                      공통 배치 담당자 조정
InformationPanel.prefab          정보 구매 화면
CompanyCard.prefab               기업 정보 카드
Scoreboard.prefab                정산 화면
```

Unity는 Scene·Prefab 등의 병합을 돕는 UnityYAMLMerge를 제공한다. 사용한다면 팀 에디터 버전에 맞게 각 PC에 설정한다. 도구가 병합에 성공해도 화면의 배치·참조·버튼 이벤트가 올바른지는 Unity에서 확인한다. [Unity 공식 Smart Merge 문서](https://docs.unity.com/en-us/engine/6000.7/manual/get-started/project-configuration/version-control/smart-merge)

### 충돌이 발생하면

1. 충돌 파일과 관련 담당자를 확인한다.
2. 두 변경의 목적을 확인하고 필요한 결과를 정한다.
3. 코드·JSON은 공통 계약에 맞춰 수정한다. Scene·Prefab은 에셋 참조까지 확인한다.
4. 충돌 표시가 남아 있지 않은지 확인한다.
5. 데이터 검증과 해당 C# 검증을 실행한다.
6. Unity에서 Scene·Prefab을 열어 Missing Script, 누락 참조, 버튼 연결, 화면 표시를 확인한다.
7. 최종 diff를 확인한 뒤 해당 파일만 커밋한다.

`.meta`를 지우고 다시 생성하거나, 전체 파일에 일괄적으로 “내 버전 사용/상대 버전 사용”을 적용해 해결하지 않는다. `.meta`의 GUID가 바뀌면 기존 Scene·Prefab의 참조가 끊길 수 있다. 원래 에셋 식별자와 필요한 참조를 유지한다. [Unity 공식 Scene·Prefab 협업 가이드](https://unity.com/blog/author-scenes-and-prefabs-with-verson-control)

문제 해결을 위해 다른 사람의 변경을 강제 삭제하거나 공유 기록을 덮어쓰는 명령을 AI에게 실행시키지 않는다. 어떤 변경을 유지할지 확인한 뒤 필요한 파일만 수정한다.

## 7. 임시 데이터와 정답을 함께 관리한다

[기존 공통 임시 데이터](../임시%20데이터%20및%20검증용/)가 기준이고, 역할별 파일은 해당 담당자가 사용할 입력·기대 결과를 정리한 패키지다. 각 담당자가 별도의 정답 복사본을 만들고 임의 수정하면 서로 다른 규칙으로 개발하게 된다.

- 단위는 bps, 날짜 인덱스·묶음 번호·필드명은 공통 연결 규약을 유지한다.
- 구현 결과가 기대값과 다르면 먼저 규칙·입력·구현을 확인한다. 검사를 통과시키기 위해 기대값부터 바꾸지 않는다.
- 규칙 변경이 합의되면 원본 데이터, 생성·검증 스크립트, 역할별 패키지, 관련 설명을 같은 PR에서 갱신한다.
- 생성 스크립트가 덮어쓰는 JSON은 생성 원본도 함께 수정한다. JSON만 수정한 뒤 재생성으로 변경이 사라지는 일을 막는다.
- 정산 기대값은 계산 근거를 PR에 적고 다른 사람이 독립적으로 검토한다.
- 각 사례는 새 상태에서 시작한다. 실패 사례의 코인·선택 상태가 다음 사례로 남지 않게 한다.
- 방장 원본 주가·모든 플레이어 구매 기록·전체 주문·정답 파일을 일반 클라이언트의 Resources·StreamingAssets에 통째로 넣지 않는다.

정보 구매 변경이라면 P1의 성공만 보지 말고 P2의 정보가 계속 숨겨지는지도 확인한다. UI에서 원본을 읽어 숨기는 방식으로 임시 구현한 경우, 실제 개인별 필터링이 된 것으로 표시하지 않는다.

## 8. 자동 확인과 실제 구현 검증을 나눈다

작업공간 루트에서 문서·데이터 패키지의 일관성을 확인한다.

```powershell
python "개발 정리/임시 데이터 및 검증용/validate_fixtures.py"
python "개발 정리/AI 개발 가이드/build_packages.py" --check
```

`--check`는 파일을 새로 만들어 정답을 덮어쓰는 용도로 사용하지 않는다. 생성이 필요하다면 생성 스크립트의 사용법을 확인하고 변경 내용을 검토한다. CI를 추가할 때도 기본 검사는 읽기·비교로 동작하게 한다.

| 확인 단계 | 증명하는 것 | 추가로 필요한 확인 |
|---|---|---|
| Python 데이터·패키지 검사 | 원본 fixture·기대값·역할별 자료가 일관적인가 | C# 구현이 같은 결과를 내는가 |
| C# 규칙 검증 | B·C 등의 실제 구현이 사례를 통과하는가 | UI·실제 통신과 연결되는가 |
| Unity 로컬 통합 | 요청→규칙→화면 갱신이 연결되는가 | 4인 접속에서 대상·순서가 맞는가 |
| 실제 4인 검증 | 방장 포함 각 플레이어에게 올바르게 전달되는가 | 인터넷 환경·중단 조건에서 동작하는가 |

Python 검사만 통과한 PR을 “멀티플레이 검증 완료”라고 적지 않는다. Unity 자동 검사를 추가하는 경우에는 사용하는 Unity 버전·필요 라이선스·실행 환경을 별도로 준비한다. 현재 제공된 Python 명령만으로 Unity가 빌드되지는 않는다.

## 9. 기능 연결 완료 체크리스트

- [ ] 최신 공통 맥락·연결 규약·역할 파일을 기준으로 개발했다.
- [ ] 공통 DTO 중복 정의와 임의 단위 변경이 없다.
- [ ] 선행 계약 PR이 `dev`에 병합되었고 최신 `dev`를 반영했다.
- [ ] 기능 PR의 대상(base)은 `dev`, 소스(compare)는 본인의 기능 브랜치다.
- [ ] 원본 fixture와 역할별 패키지 검사를 통과했다.
- [ ] 역할별 통과기준을 실제 C# 구현에 적용하고 결과를 남겼다.
- [ ] 실패 시 코인·자리·주문 상태가 바뀌지 않는다.
- [ ] 같은 요청의 재전송이 규칙을 두 번 실행하지 않는다.
- [ ] 방장 자신의 행동도 다른 참가자와 같은 요청 경로를 거친다.
- [ ] 개인 정보는 요청자에게만, 공개 정보는 필요한 전체 참가자에게 전달된다.
- [ ] D는 응답의 자산·코인을 표시하며 자체적으로 최종 상태를 확정하지 않는다.
- [ ] 변경한 Scene·Prefab·.meta의 참조를 Unity에서 확인했다.
- [ ] Mock으로 남은 부분과 실제로 연결한 부분을 PR에 구분했다.
- [ ] 4인 실행 여부와 아직 확인하지 못한 항목을 기록했다.

매일 최소 한 번 최신 `dev`에서 정보 구매→기업 선택→주문 확정→정산 흐름을 확인한다. 아직 구현되지 않은 단계가 있다면 현재 연결 가능한 구간까지만 확인하고, 그 범위를 기록한다. 마지막 병합은 새 기능 추가보다 한 턴을 끝까지 실행하는 결과를 기준으로 판단한다.
