# 4인 AI 개발 패키지 사용법

이 폴더는 네 명이 각각 다른 AI 모델에 작업을 맡겨도 같은 게임 규칙·데이터 형식·담당 경계로 개발하도록 만든 자료다. Unity 게임 코드 자체나 완성된 네트워크 구현은 포함하지 않는다.

현재 문맥은 `prototype-v2`, 규칙은 `rules-v2`다. [02_결정_사항.md](./02_결정_사항.md)는 사용자 위임으로 작성한 **확정 기록**이다. 이전 prototype-v1 파일을 AI에 계속 첨부하지 말고 새 공통문서와 역할 JSON을 함께 전달한다.

## AI에게 전달할 파일

네 사람 모두 아래 공통 문서를 먼저 제공한다.

1. [00_공통_맥락.md](./00_공통_맥락.md): 게임·개발 범위·단위·임시 정책.
2. [01_공통_연결_규약.md](./01_공통_연결_규약.md): 상태의 소유자, 요청·응답, 기능 연결 방식.
3. [02_결정_사항.md](./02_결정_사항.md): 원문 충돌을 해소한 날짜·입찰·효과·시간 초과 등의 확정 규칙.
4. [03_GitHub_병합_지침.md](./03_GitHub_병합_지침.md): 브랜치·리뷰·Unity 충돌·검증.

그다음 본인 담당 폴더의 세 파일을 추가한다.

| 담당 | 작업 지침 | 개발할 때 넣을 입력 | 통과해야 할 기대 결과 |
|---|---|---|---|
| A: 멀티·진행 | [A/작업지침.md](./A/작업지침.md) | [A/임시데이터.json](./A/임시데이터.json) | [A/통과기준.json](./A/통과기준.json) |
| B: 시장·투자·정산 | [B/작업지침.md](./B/작업지침.md) | [B/임시데이터.json](./B/임시데이터.json) | [B/통과기준.json](./B/통과기준.json) |
| C: 정보·코인 | [C/작업지침.md](./C/작업지침.md) | [C/임시데이터.json](./C/임시데이터.json) | [C/통과기준.json](./C/통과기준.json) |
| D: UI·그래프 | [D/작업지침.md](./D/작업지침.md) | [D/임시데이터.json](./D/임시데이터.json) | [D/통과기준.json](./D/통과기준.json) |

`임시데이터.json`에는 파일 목록만 있는 것이 아니라 해당 역할이 사용하는 실제 데이터와 사례별 초기 상태·요청이 들어 있다. `통과기준.json`에는 대응되는 기대 상태·응답·정산값과 수동 통합 점검표가 들어 있다. 파일을 AI에 첨부해도 되지만, 실행 중인 게임 클라이언트에 정답 파일을 넣지는 않는다.

이 JSON은 AI·테스트 드라이버용 묶음이며 게임의 통신 DTO 자체가 아니다. 예를 들어 `inputs["C_information_before.json"].data`가 원래 서버 상태다. Unity에서는 그 안의 원본 형식을 공통 DTO로 읽거나 기존 원본 파일을 직접 읽는다. 바깥쪽 파일명별 맵 전체를 `JsonUtility`의 일반 Dictionary DTO로 바로 읽을 수 있다고 가정하지 않는다. `sourcePath`는 작업공간 루트 기준이며 역할 폴더 기준 상대경로가 아니다.

## 복사해서 사용할 시작 프롬프트

```text
나는 투자 게임의 [A/B/C/D] 담당 개발자다.
공통 맥락, 연결 규약, 규칙 확정 기록, GitHub 지침과 내 역할의 작업지침·임시데이터·통과기준을 읽어라.
현재 저장소의 실제 Unity 버전·패키지·공통 DTO·인터페이스·기존 변경을 먼저 확인해라.
지금 작업은 [Issue와 완료 조건]이다. 기준 브랜치/커밋은 [기재]다.
내 담당 범위에서 구현하고, 다른 담당자의 규칙을 복제하거나 공통 DTO를 임의로 바꾸지 마라.
공통 기반이 없으면 필요한 계약을 먼저 구체적으로 제안하고, 승인된 공통 기반과 맞는 임시 구현을 사용해라.
fixture의 임시 가정을 정식 기획으로 취급하지 말고, 후순위 기능을 이번 작업에 끼워 넣지 마라.
입력 데이터를 실제 구현에 넣은 결과를 통과기준과 비교해라. 기대값을 구현에 맞춰 고치지 마라.
변경 파일, 입력·출력 변경, 실행한 검증과 결과, 미실행 검증, 남은 연결 지점을 보고해라.
커밋·푸시·PR·병합은 이번 요청에서 허용한 범위만 수행해라.
```

원격 AI가 로컬 파일을 읽을 수 없다면 위 공통 4개와 본인 폴더의 3개를 함께 첨부한다. 실제 구현 시작 시에는 최신 Shared 코드와 해당 Issue도 제공해야 한다. 이 패키지만으로 현재 저장소 코드를 추측해서 새 DTO를 만들지 않는다.

## 무엇이 이미 검증되었나

- 원본 임시 데이터 16개의 일관성과 34개 참조 사례는 기존 Python 검증 대상으로 유지한다.
- 역할별 입력·기대값은 그 원본에서 추출했다. 원본 JSON을 이 폴더에서 직접 수정하지 않는다.
- 새 패키지 검사는 원본과 추출본의 일치·모든 사례의 담당 배정·문서 링크·필수 파일을 확인한다.
- Unity 실행, C# 구현의 결과, 실제 4인 RPC, 타이머·시간 초과·재접속은 아직 실행한 검증이 아니다. `통과기준.json`의 `integrationChecks`는 앞으로 구현을 넣어 확인할 기준이다.

## 검증과 갱신

작업공간 루트에서 실행한다.

```powershell
python ".\개발 정리\임시 데이터 및 검증용\validate_fixtures.py"
python ".\개발 정리\AI 개발 가이드\build_packages.py" --check
```

원본 기획·임시 데이터가 바뀌면 `source_snapshot.json`의 SHA-256과 비교하여 변경을 감지한다. 변경된 기획은 공통·역할 문서에 검토 반영한 뒤 아래 명령으로 패키지 JSON과 스냅샷을 갱신한다.

```powershell
python ".\개발 정리\AI 개발 가이드\build_packages.py" --write
python ".\개발 정리\AI 개발 가이드\build_packages.py" --check
```

`--write`는 이 폴더의 역할별 JSON 8개와 원본 스냅샷을 덮어쓴다. 공통·역할 Markdown을 자동으로 최신 기획에 맞게 고치는 명령은 아니다. CI·리뷰에서는 `--check`만 실행하여 원본 변화를 조용히 덮어 감추지 않는다.

검증 근거는 [개발 프로세스](../참고사항/전체%20프로세스%20정리.md), [7주차 정리](../../7주차%20발표정리/7주차%20정리.md), [요구사항명세서](../../요구사항명세서/요구사항명세서.MD), [7주차 발표](../../7주차%20발표정리/7주차%20발표.pptx)다. 개발 프로세스는 rules-v2와 현재 개발·검증·dev PR 흐름을 통합한 안내서이며, 세부 규칙은 공통 확정 기록과 함께 관리한다.
