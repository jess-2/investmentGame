# D 담당 AI: 화면·그래프·사용자 입력

먼저 [공통 맥락](../00_공통_맥락.md), [연결 규약](../01_공통_연결_규약.md), [규칙 확정 기록](../02_결정_사항.md), [GitHub 지침](../03_GitHub_병합_지침.md)을 읽는다. [임시데이터.json](./임시데이터.json)은 UI의 실제 시작 상태·도착 이벤트, [통과기준.json](./통과기준.json)은 기대 화면 상태와 점검표다.

## 담당 기능과 범위

|---|---|---|
| P0 | 참가·대기 화면 | A의 연결 상태·4명·준비 여부 표시, 방 생성/참가 입력 |
| P0 | 기업 카드 6개 | REQ-005/018. 위3개·아래3개, 기업명·잔석·개인 정보 표시 |
| P0 | 정보 구매창 | 기업·묶음 선택→구매 요청, 코인 표시, 구매중·성공·실패 |
| P0 | 일별 그래프 | bps→퍼센트, 날짜별 값, 미열람 구간 잠금·공백 |
| P0 | 기업 선택·투자 주문창 | 자기 차례 안내, 비율·진입·청산 입력, 본인 확정 주문 표시 |

D는 서버 코인·손익·열람 권한을 직접 확정하지 않는다. 클라이언트 입력 검증으로 잘못된 값 선택을 줄일 수 있으나 최종 검증은 A/B/C가 수행한다. 화면에서 막았다는 이유로 서버 검증을 생략하지 않는다.

## 입력과 기대 상태 구분

- `inputs.D_public_initial.json`: 참가자·INFO단계·잔석2개.
- `inputs.D_P1_before_purchase.json`: P1 코인3개·기업별 공개2묶음. 자산10,000.
- `inputs.D_P2_after_P1_purchase.json`: P2 비교 화면 입력. P1 구매 정보 없음.
- `incomingEvents`: 구매 응답·8회 자리 갱신·주문 확정 응답을 시간 순으로 주입할 수 있다. 서로 다른 단계의 이벤트는 공통 문맥과 맞춰 별도 시나리오로 실행한다.
- `selectionReplay`: 기업 선택 버튼이 만드는 요청의 비교 입력이다. `selectionResults`에는 단계별 부분 결과가 있으며 완전한 통신 envelope는 Shared 선언에 맞춘다.
- `testActions`: P1이 AI 1번 묶음을 구매하는 요청 등. 실제 버튼이 만드는 객체와 비교한다.
- `referenceCases`: 구매 실패/잘못된 주문의 setup은 서버 내부 데이터다. UI에 그대로 주지 말고 Mock이 응답할 오류를 만드는 테스트 드라이버용으로만 사용한다.
- `통과기준.json.expectedSnapshots`: 구매 후 P1 전체 개인뷰, P2 불변뷰, 선택 완료 공개 상태, 정산 전광판의 정답.

UI 입력 JSON에 원본 시장 전체를 넣지 않았다. D는 원본을 읽지 않고 자기 역할 파일만으로 기본 화면을 만들 수 있다. 정산 전광판은 서버가 확정한 공개 결과이므로 정답이자 렌더링 입력으로 사용 가능하다.

## 실제 구매 화면 예시

1. P1 구매 전 데이터를 로드하면 `coins: 3`을 표시한다.
2. AI 1번 묶음(6~10일)을 선택하고 구매하면 공통 `BUY_INFORMATION` 요청을 만든다.
3. 응답이 오기 전에는 해당 요청을 대기 표시한다. 잔액을 미리 최종 확정하지 않는다.
4. 성공 응답의 `remainingCoins: 2`를 적용한다. 같은 응답을 다시 받아도 `coins -= 1`처럼 중복 차감하지 않는다.
5. 받은 5개 값을 AI의 해당 묶음에 합친다. 다른 기업·기존 무료 정보는 유지한다.
6. 그래프에는 6일 -15%, 7일 -20%, 8일 -25%, 9일 -30%, 10일 -40%를 날짜와 맞춰 표시한다.
7. P2 화면은 계속 코인3개이며 해당 묶음이 없다. 방장 화면도 P1 필터뷰만 사용한다.

## 그래프와 투자 화면에서 주의할 점

- `visibleBundles`에 없는 묶음을 0%로 그리지 않는다. 숨겨진 구간을 선으로 이어 실제 관측값처럼 표시하지 않는다.
- 축·툴팁·최고/최저 표시도 미공개 원본을 참조하지 않는다. 축은 설정값 또는 현재 열람값에 기반해 정한다.
- 묶음 첫 날짜는 `startDay`, 이후 매일 1씩 증가한다. 5개짜리 배열 인덱스0을 0일차로 그리지 않는다.
- 첫 기업 60%·둘째40%처럼 배열 순서와 비중을 유지한다. UI 정렬 때문에 투자 비중이 바뀌지 않아야 한다.
- 두 번째 기업과 최대2개 구간 입력을 지원한다. 날짜는 정수 일별, 보유기간5~10일이며3→8·3→13일을 허용한다. 이미 보유한 정보의5일 묶음 경계로 날짜를 제한하지 않는다.
- 자리 갱신에서는 남은 자리와 현재 차례만 표시한다. 타인 기업·금액·구간 명단을 임의 추가하지 않는다.
- 전광판의 P1 `4280bps`는 +42.8%, P3 `-1100bps`는 -11%. 금액과 퍼센트를 구분한다.
- 타이머는 표시이며 진행 판정은 A. 일반 INFO50초·차례당4초·주문23초, 입찰턴 INFO35초와 입찰15초. 자동 기업·50:50/0~5일 기본 주문 표시도 제공한다. fixture 수동 모드는 실제 timeout 완료 증거가 아니다.

## 구현 순서와 담당자 연결

1. 공통 서비스와 같은 입력·출력의 `MockGameService`를 UI 개발용으로 주입한다.
2. 고정 성공만 반환하지 말고 테스트별 코인부족·중복·시간지연 응답도 제공한다. Mock은 독립 시나리오마다 초기화한다.
3. UI Prefab과 Presenter/ViewModel 등 화면 갱신을 분리해 데이터 주입만 바꿀 수 있게 한다. 구조 이름은 팀 코드에 맞춘다.
4. A의 실제 클라이언트 서비스로 교체하고 요청 이벤트·개인 응답·공개 갱신을 연결한다. C/B를 UI에서 직접 호출하는 호스트 전용 경로를 만들지 않는다.
5. 자기 차례 외 버튼, 늦게 도착한 이전 턴 응답, 실패 후 잔액 유지, 재응답 중복 적용을 확인한다.
6. `integrationChecks`의 UI별 실제 동작·화면 기록을 남긴다. 서버 참조 사례가 모두 통과해도 UI 검증을 대신하지 못한다.

권장 경로 예시: `Assets/Scripts/UI`, `Assets/Prefabs/UI`, `Assets/Tests/UI`. 공통 메인 Scene 편집은 A와 시점을 조율하고 각 화면은 Prefab으로 나눈다. 새 에셋과 `.meta`를 함께 전달한다.

## 다른 담당자에게 요청할 것

| 대상 | 필요한 것 |
|---|---|
| A | 실제 클라이언트 서비스·이벤트 구독·신원·턴·단계·마감시간 |
| C | 개인뷰와 구매 성공/실패 결과, 상태·필드 의미 |
| B | 본인 주문 확인 데이터와 공개 전광판 결과 |

임시 데이터가 끝나면 화면도 다시 만드는 것이 아니다. 입력·응답 계약은 유지하고 Mock 공급자만 실제 서비스로 교체하는 것이 목표다.
