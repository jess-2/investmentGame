# C 담당 AI: 정보·코인·개인 열람 상태

먼저 [공통 맥락](../00_공통_맥락.md), [연결 규약](../01_공통_연결_규약.md), [규칙 확정 기록](../02_결정_사항.md), [GitHub 지침](../03_GitHub_병합_지침.md)을 읽는다. [임시데이터.json](./임시데이터.json)과 [통과기준.json](./통과기준.json)을 함께 사용한다.

## C가 실제로 구현할 기능

| 우선순위 | 기능 | 책임 |
|---|---|---|
| P0 | 구매 조건 검사 | 유효 기업·묶음, 열람 여부, 코인, 턴·단계 |
| P0 | 코인 차감과 구매 기록 | 둘을 하나의 처리로 확정. 실패 시 둘 다 유지 |
| P0 | 공개 정보·개인 정보 조합 | B의 동일한 공개 묶음과 본인 구매 기록으로 개인뷰 생성 |
| P0 | 구매 결과 반환 | 남은 코인·구매한 5일 값·실패 코드. 전체 시장 반환 금지 |
| P1 | 턴당 코인 지급·이월 | A의 턴 시작 호출을 받아 3/5개 지급, 지급 원장으로 중복 방지 |
| P1 | 턴별 열람 기록 | 다음 턴 시장으로 이전 구매 정보가 새지 않도록 턴으로 구분 |
| 후속 | 아이템·입찰·고유능력 | REQ-008~017은02의 확정 가격·효과·순서로 후속 작업. 기본 NONE 데이터와 효과 테스트를 분리 |

REQ-004와 REQ-005의 정보 규칙을 담당한다. **코인 3→2와 해당 정보 열람 권한 변경을 구현하는 사람은 C**다. A가 통신으로 C를 호출하고, D가 C의 결과를 표시한다. B는 원본 시세만 제공한다.

## 입력 데이터와 기대 상태

- `00_rules.json`: 묶음 가격 1, 초기3개, 지급량 전환 등 확정 규칙. 고정 데이터는 재현용이다.
- `B_market_server.json`: B의 서버 전용 원본. C가 새 시세를 생성하지 않는다.
- `C_information_before.json`: 네 사람 코인3개·구매 없음. 이미 1턴 코인이 지급되었으므로 다시 지급하지 않는다.
- `exchange_examples.json`: P1의 AI 1번 묶음 구매 요청. 1번은 6~10일.
- `referenceCases`: 구매 관련 9개·코인지급 3개. 같은 요청 재전송은 A와 함께 검증한다.

P1 구매 성공 뒤 기대값:

```json
{
  "playerId": "P1",
  "coins": 2,
  "purchasedBundles": [{"companyId": "AI", "bundleIndex": 1}]
}
```

반환할 값은 `[-1500,-2000,-2500,-3000,-4000]`, 첫날은 `startDay: 6`. 구매 전/후 서버 상태는 `expectedSnapshots`의 C 파일, 개인뷰는 D 파일과 비교한다. `purchasedBundleCount`는 변경 후 총 구매 묶음 수다.

## 개인뷰 생성 경계

1. 무료 묶음 위치는 B에서 읽는다. 플레이어마다 재추첨하지 않는다.
2. 해당 턴·해당 플레이어의 구매 원장만 합친다.
3. 볼 수 있는 묶음만 `visibleBundles`에 넣는다. 미열람 묶음은 값0을 채워 넣지 않는다.
4. 원본 배열과 반환 배열은 참조를 공유해 외부에서 원본을 수정할 수 있게 하지 않는다.
5. `source`는 `PUBLIC` 또는 `PURCHASED`, `startDay`는 `bundleIndex * 5 + 1`.
6. P1 구매 뒤에도 P2뷰에는 그 묶음이 없어야 한다. 방장 P1도 똑같이 필터링한다.
7. 개인뷰의 자산·본인 주문은 B의 읽기 결과를 조합한다. C가 투자 손익이나 타인 주문을 관리하지 않는다.

## A·B·D와 연결할 방식

```text
D가 구매 의도 전송
→ A가 실제 요청자·문맥을 확인
→ C가 잔액·열람을 검사
→ B의 시장 조회로 기존 5일 값 확인
→ C가 차감·원장 추가와 결과 생성
→ A가 본인에게만 전송
→ D가 화면 갱신
```

신원은 A가 확인한 것을 받는다. `remainingCoins` 같은 클라이언트 주장값을 서버 잔액으로 대입하지 않는다. 정보조회나 검증 실패가 구매기록·차감만 남기지 않게 한다. 동일한 요청은 A의 캐시에서 재응답하되 C도 구매 원장으로 중복 차감을 방어한다.

## 독립 개발과 완료 기준

1. 임시 시장 조회 구현과 구매 전 원장을 메모리에 로드한다.
2. 구매 요청을 실제 C# 기능에 직접 넣고 서버 기대 상태·응답·P1/P2뷰를 비교한다.
3. A 연결 전에는 로컬 호출로 규칙 검증을 끝낸다. A 연결 후 같은 결과가 개인 수신자에게 전달되는지 확인한다.
4. `통과기준.json.integrationChecks`의 조회 실패 무변경, 턴 이월·원장 분리, 동시 구매, 원본 불변성까지 구현 검증한다.
5. UI 담당자에게 성공/실패 응답 DTO·개인뷰·오류 코드와 실행 방법을 제공한다. 매번 JSON 파일을 생성해 전달하는 실제 기능으로 해석하지 않는다.

초기 fixture 지급 원장과 실제 초기화 전략은 A와 함께 정한다. `lastGrantedTurn = 1`에 해당하는 상태를 복원하지 않으면 첫 로드에서 3개를 다시 주는 오류가 발생한다. 같은 턴을 두 번 시작해도 잔액이 증가하지 않는지 검사한다.

권장 경로 예시는 `Assets/Scripts/Rules/Information`, `Assets/Tests/Rules/Information`. 실제 코드 경로는 프로젝트에 맞추되 UI·네트워크 의존을 분리한다. 기본 시제품은 `inventory: []`, `abilityId: "NONE"`으로 유지한다. 후속 개발에서는 상점 턴당1회·인벤토리3개·금융/정보/공격 각1회와02의 확정 가격·효과를 적용한다. 무료 능력권으로 얻은 정보는 ABILITY, 아이템은 ITEM, 훔친 정보는 STOLEN으로 구분하고 유료 PURCHASED만 공격의 유료정보 대상으로 사용한다.
