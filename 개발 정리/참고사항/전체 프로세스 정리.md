> 갱신: 2026-10-26 · 문맥 `prototype-v2` · 게임 규칙 `rules-v2` · 임시 JSON 형식 `schemaVersion: "1.0"`
>
> 팀원이 전체 게임 규칙, 담당 기능과 연결, 개발·검증·PR 흐름을 한곳에서 확인하기 위한 안내서다. “구현 예정”은 실제 Unity 구현이나 검증이 완료됐다는 뜻이 아니다.

## 1. 자료의 기준과 이번 정리의 범위

기획의 출발점은 [7주차 발표 PPT](../../7주차%20발표정리/7주차%20발표.pptx)와 [7주차 정리](../../7주차%20발표정리/7주차%20정리.md)다. PPT에 남아 있는 이전 수치, 서로 다른 설명, 당시 비어 있던 정책은 사용자 지시·위임으로 정리한 [게임 규칙 확정 기록](../AI%20개발%20가이드/02_결정_사항.md)의 `rules-v2`를 적용한다. 현재 7주차 정리 Markdown에도 rules-v2가 반영되어 있으므로 두 파일을 모두 변경 전 자료로 취급하지 않는다.

`02_결정_사항.md`는 현재 채택한 **초기 규칙의 확정 기록**이다. 사용자가 직접 정한 정보·날짜 규칙과, 위임받아 정한 초기 자산·효과·타임아웃 등의 설정을 포함한다. 밸런스 수치는 플레이 테스트 후 팀 합의로 바꿀 수 있으며 문서·데이터·구현을 함께 갱신한다. 이번 정리에서 새로운 게임 규칙을 추가하지 않는다.

## 2. 게임 전체 구조와 구현 순서

블랙웨일 증권이 빚을 진 참가자들을 모아 비밀 투자대회를 연다. 최종 승자에게 빚 탕감과 보상을 제공한다. 이전 PPT의 데스게임 분위기를 근거로 사망·탈락 기능을 추가하지 않는다.

- 참가자는 4명, 기업은 `AI`, `SPACE`, `FOOD`, `BANK`, `BIO`, `AUTO` 6개다.
- 한 게임은 10턴이다. 한 턴은 가상 30일, 실제 최대 120초다.
- 정보 해석·구매 후 기업과 거래 구간을 사전 확정하고 시장 공개 후 정산한다. 실시간 매매로 구현하지 않는다.
- Unity에서 방장 1명이 서버와 플레이어를 함께 맡고 참가자 3명이 접속한다.
- 테스트 참가자는 `P1~P4`이며 P1이 방장이다. 개발 담당 A/B/C/D, 투자 선택 자리 A/B/C/D와 구분한다.

```text
게임 시작: 4인 접속·준비 → 초기 순서·타이브레이크 순번 추첨
           [후속: 능력 후보 제시·선택]

매 턴: 지원·코인 지급 / 시장 생성 / 자리 배정
       → [3·6·9턴 입찰]
       → INFO 정보 탐색·구매
       → SELECTION 기업 선택 8회
       → INVESTMENT 비율·진입·청산 확정
       → 주문 잠금 → MARKET_REVEAL 시장 공개
       → RESULT 정산·전광판·보상
       → 다음 턴 또는 10턴 종료 후 최종 승자 결정
```

규칙 확정과 시제품 구현 범위를 구분한다.

| 구현 단계 | 포함할 기능 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 공통 기반 | Unity 세부 버전·패키지 확인, Shared DTO·서비스 경계·실행 모드 | 전원이 같은 계약 사용 |
| 고정 1턴 | 접속·준비, 정보 구매, 8회 기업 선택, 주문, 공개, 정산·전광판 | 기본 기대값 일치, 개인 정보 분리 |
| 실제 진행 확장 | 실제 타이머·자동 행동, 복수 턴·코인 이월, 1~8턴 자리 순환, 난수 시장 | 실제 4인으로 3턴, 이후 10턴 검증 |
| 안정화 | 중복·동시 요청, 연결 종료·재접속, 오류 안내·경계값 | 관련 실제 구현 검증 기록 |
| 후속 효과 | 증폭기 1종부터 입찰·나머지 아이템·능력·파산/재기 지원 확장 | 기능별 별도 사례와 통합 검증 추가 |

정보 구매도 기본 1턴에 포함한다. 입찰·능력 등은 확정됐어도 기본 fixture에서 검증하지 않는다. 일정이 부족하면 구현 범위와 시연 모드를 명시한다.

## 3. 개발 담당과 상태 변경 책임

각 담당자가 만든 코드는 하나의 게임으로 합쳐진다. A/B/C/D가 서로 다른 PC 에서 서버를 나눠 실행하는 뜻이 아니다. 방장 PC 에서 A의 서버 진행 코드와 B/C의 규칙 코드가 실행되고 각 플레이어의 D 화면이 서버에 요청한다.

| 담당 | 직접 변경하는 상태·구현 기능 | 다른 담당자와의 연결 |
|---|---|---|
| **A: 멀티·진행** | 접속·방장·준비, 턴·단계·자리 배정·선택 차례·마감시간, 요청 캐시·라우팅 | D 요청 확인 후 B/C 호출. B 선택 성공 후 차례 전진. C에 코인 지급, B에 시장 준비·주문 잠금·정산 지시 |
| **B: 시장·투자·정산** | 전체 시장·무료 묶음 위치, 선택 기업 원장·정원, 주문·자산·손익·순위 | A 문맥으로 규칙 처리. C에 묶음·본인 자산/주문 조회 제공. 공개 성과는 A 경유로 D에 전달 |
| **C: 정보·코인·효과** | 코인·지급 원장, 턴별 구매·열람 기록·개인뷰. 후속 상점·인벤토리·능력·효과 사용 기록 | B 시장 조회 사용, 구매 결과를 A에 반환. 비용·정산 효과는 B와 연결하고 자산 원장을 별도로 복제하지 않음 |
| **D: UI·그래프** | 버튼·선택·요청 대기, 화면 캐시·그래프·타이머·전광판 | 클라이언트 서비스로 A에 요청, 서버 응답으로 표시 갱신. B/C 규칙을 UI에서 다시 계산하지 않음 |

A도 진행 상태를 직접 관리한다. “상태 변경은 전부 B/C, A는 전달만 담당”으로 이해하지 않는다. 반대로 A가 손익·코인 차감을 복제하지 않는다.

B/C는 UI·GameObject·RPC 에 의존하지 않는 일반 C# 규칙 계층으로 만든다. A가 호출을 조정하고 D는 같은 입력·출력의 클라이언트 서비스를 사용한다. 실제 클래스·파일 경로는 저장소를 먼저 확인하며 제안 경로를 기존 코드로 가정하지 않는다.

### 요청 전달 방식

```text
각 플레이어의 D 화면
  → 네트워크 요청 → 방장 서버 A
  → 서버 내부 B/C 함수 호출 → 결과 반환
  → 개인 응답 또는 공개 갱신 전송 → D 화면 갱신
```

D↔A는 네트워크 메시지, A↔B/C는 보통 C# 객체를 넘기는 내부 함수 호출이다. JSON 문자열 사용 여부는 통신 구현에 따른다. 매 클릭마다 JSON 파일을 만들어 전달하지 않는다. 현재 JSON 은 개발용 입력·기대 결과와 형식 예시다.

방장 P1의 UI도 같은 검증 경로와 개인뷰를 사용한다. 호스트 화면이 서버 원본을 직접 읽는 별도 경로를 만들지 않는다.

## 4. 턴 진행·타이머·시간 초과

| 단계 | 일반 턴 최대 | 3·6·9턴 최대 | 서버 처리 | 담당 연결 |
|---|---:|---:|---|---|
| 시작 처리 | 0초 | 0초 | 지원 후 턴 시작 자산 S 고정, 코인 지급, 시장·원장 준비·자리 배정 | A가 B/C 호출 |
| AUCTION | 없음 | 15초 | 입찰·선호 확정, 비용·아이템·자리 반영 | 후속 A 진행 / C 규칙 / B 자산 / D 입력 |
| INFO | 50초 | 35초 | 정보 구매. 후속 정보형·공격형 사용 | A 문맥 / C 구매 / B 시장 / D 화면 |
| SELECTION | 32초 | 32초 | 8회 선택, 차례당 최대 4초 | A 차례 / B 선택·정원 / D 입력 |
| INVESTMENT | 23초 | 23초 | 비율·구간 확정. 후속 금융형 사용 | A 마감 / B 주문 / C 효과 / D 입력 |
| MARKET_REVEAL | 10초 | 10초 | 주문 잠금 후 공개·연출 | A 전환 / B 원본·잠금 / D 그래프 |
| RESULT | 5초 | 5초 | 정산·순위·후속 보상·다음 턴 또는 종료 | B 계산 / C 보상 / A 전달 / D 표시 |
| **합계** | **120초** | **120초** | 조기 완료 가능 | 시간 판정은 A |

- 서버 수신 시각이 마감보다 일러야 한다. 정확히 마감 시각에 도착한 새 요청은 거절한다. 이전에 처리된 동일 요청의 재전송은 캐시만 반환한다.
- 선택 성공 즉시 다음 차례로 넘어가며 새 4초를 준다. 다른 단계도 전원 완료 시 조기 진행할 수 있다. 남은 시간을 다음 단계로 적립하지 않는다.
- D는 A의 서버 경과·마감시간으로 남은 시간을 표시하고 완료 의도를 보낸다. 로컬 타이머로 단계·정산을 직접 진행하지 않는다.
- `phaseEndsAtServerSeconds`는 선택 단계 전체 상한, `selectionDeadlineAtServerSeconds`는 현재 선택자 마감이다. 후자는 다른 단계에서 0이다.

| 미입력·시간 초과 | 자동 행동 |
|---|---|
| 기업 선택 | `BANK→FOOD→AUTO→AI→SPACE→BIO` 중 잔석이 있고 본인이 고르지 않은 첫 기업 |
| 투자 주문 | 확정 주문 유지. 미제출자는 선택 기업 순서대로 50:50·각 0→5일 1구간 |
| 정보 탐색 | 추가 구매 없이 진행 |
| 후속 입찰 | 미제출액 0, 자리 선호 누락·오류는A→B→C→D |
| 후속 능력 선택 | 제시된 첫 후보 |

A가 자동 행동을 서버 명령으로 만들어 B/C의 같은 규칙을 호출하고 본인에게 자동 처리 표시를 보낸다. 비공개 시장으로 유리한 기업·날짜를 대신 고르지 않는다.

`MANUAL_FOR_FIXTURE`는 재현용으로 자동 진행을 멈춘 모드다. 타이머 미정이나 실제 마감 검증 완료를 뜻하지 않는다. 선택 replay는 INFO50초 후 선택당 3초를 사용해 74초에 주문 단계, 97초에 주문 마감으로 가는 조기 진행 예시다.

## 5. 정보·황금 코인·구매 기능

### 정보와 코인 규칙

- 서버 시장은 기업별 0~30일 값 31개다. 각 값은 **0일차 대비 변화율**이며 0일차 0%는 전원 공개다.
- 정보는 1~5일, 6~10일, 11~15일, 16~20일, 21~25일, 26~30일의 6묶음이다. 묶음마다 날짜별 값 5개다.
- 전체 6기업은 36묶음·일별 180개 값이다. 0일차 기준값 6개는 별도다.
- 기업마다 무료 2묶음을 서버가 한 번 추첨해 전원에게 동일 공개한다. 고정 테스트만 위치를 고정한다.
- 추가 1묶음은 황금 코인 1개다. 정보 구매는 게임머니를 사용하지 않는다.
- 1~5턴 시작 3개, 6~10턴 시작 5개 지급. 이월·상한 없음. 지급량은 구매 횟수 제한이 아니다.
- 이미 열람 가능한 정보는 `ALREADY_VISIBLE`로 거절·차감 없음. 같은 턴 지급 재호출도 잔액을 늘리지 않는다.
- 열람 원장은 턴별 분리한다. 지난 턴 결과·본인 열람정보는 읽기 전용으로 보관하되 이전 구매권으로 새 시장을 열지 못한다.

### P1이 AI 6~10일 정보를 구매하는 예

| 순서 | 담당 | 처리·데이터 |
|---|---|---|
| 1 | D | AI·묶음 1 선택, `BUY_INFORMATION` 생성, 대기 표시 |
| 2 | A | 실제 연결로 P1 확인, 턴·INFO·중복 검사 후C 호출 |
| 3 | C | 기업·묶음·열람·잔액 검사 후B에서 값 조회 |
| 4 | B | 기존 AI 시장의 6~10일 반환. 시장 재생성 없음 |
| 5 | C | 코인 3→2와 구매 원장 추가를 함께 확정·결과 반환 |
| 6 | A | 결과를P1에게만 전송 |
| 7 | D | 반환 잔액 2 적용, 기존 정보에 새 묶음 추가·그래프 갱신 |

요청·응답은 [exchange_examples.json](../임시%20데이터%20및%20검증용/exchange_examples.json)을 따른다. 묶음 번호는 0부터 시작한다.

```json
{
  "type": "BUY_INFORMATION",
  "requestId": "info-001",
  "turn": 1,
  "payload": {"companyId": "AI", "bundleIndex": 1}
}
```

```json
{
  "type": "BUY_INFORMATION_RESULT",
  "requestId": "info-001",
  "turn": 1,
  "success": true,
  "errorCode": "",
  "payload": {
    "remainingCoins": 2,
    "companyId": "AI",
    "bundleIndex": 1,
    "startDay": 6,
    "dailyChangesBps": [-1500, -2000, -2500, -3000, -4000]
  }

```

조회 실패·코인 부족·재구매 시 코인과 구매 원장 모두 유지한다. P2~P4는 코인 3개이며 P1 구매 정보가 보이지 않아야 한다. 반환 배열 수정도 B 원본·다른 개인뷰에 영향을 주지 않아야 한다.

D는 부분 응답으로 기존 정보를 지우지 않고 묶음을 합친다. 같은 응답을 다시 받아도 `coins -= 1`로 중복 차감하지 않고 반환 잔액을 적용한다. 이전 턴 응답으로 현재 화면을 덮어쓰지 않는다.

그래프 날짜는 `startDay`부터 하루씩 증가시킨다. `visibleBundles`에 없는 구간은 공백·잠금으로 표시하고 0%를 채우거나 선으로 잇지 않는다. 축·툴팁·최고/최저도 비공개 원본을 읽지 않는다.

## 6. 투자 자리·기업 선택·주문

### 자리 배정과 우선권

초기 참가자 순서는 시작 때 한 번 추첨한다. 다음은 P1/P2/P3/P4 순서라는 테스트 예시다. 1~8턴은 매 턴 재추첨하지 않고 순환한다.

| 턴 | 자리 A | 자리 B | 자리 C | 자리 D |
|---|---|---|---|---|
| 1·5 | P1 | P2 | P3 | P4 |
| 2·6 | P2 | P3 | P4 | P1 |
| 3·7 | P3 | P4 | P1 | P2 |
| 4·8 | P4 | P1 | P2 | P3 |

선택은 **자리A→B→C→D→D→C→B→A**다. 9턴 시작 입찰로 9·10턴 자리를 결정하며 배치를 유지한다. 기본 fixture는 1턴 고정 순서만 검증하고 순환·입찰은 별도 구현·검증한다.

A는 자리·차례, B는 선택 원장·정원을 관리한다. B의 선택 성공 후에만 A가 차례를 전진시킨다. 실패 시 원장·잔석·차례 유지. D는 본인 차례·잔석과 선택 버튼을 제공한다.

### 주문 검증

- 매 턴 **서로 다른 기업 2개**, 기업당 최대 2명이다.
- 비중은 5:5·6:4·7:3. 첫 기업 `weightBps`는 5000/6000/7000 중 하나, 둘째는 나머지로 합 10000이다. 30:70은 기업 순서를 바꿔 표현한다.
- 기업 배열을 임의 정렬하지 않는다. 비중과 원금 잔액 배분에 순서 의미가 있다.
- 기업별 거래 1~2구간, 정수 날짜, `0 <= 진입일 < 청산일 <= 30`, `5 <= 청산일-진입일 <= 10`이다.
- 3→8·3→13 허용, 3→7·3→14·26→31·소수 날짜 거절. 정보 묶음 경계로 거래 날짜를 제한하지 않는다.
- 미열람 날짜도 위험을 감수하고 선택 가능하다. 겹침·중복 금지, 앞 청산일=다음 진입일 허용.
- 두 구간은 같은 배정 원금에 수익률 합을 적용하고 중간 이익을 재투자하지 않는다.
- 주문 확정만으로 자산을 바꾸지 않는다. 시장 공개 전 잠금, 공개 후 변경 금지, 정산은 같은 턴에 한 번만 자산 적용한다.

## 7. 시장 생성·정산·전광판

### 시장 생성

B가 턴마다 시장을 한 번 생성·유지한다. 구매·재접속 시 재생성하지 않는다. 일별 증감은 정수bps 균등 난수로 추첨해 전일의 0일차 대비 값에 더하고 아래 범위로 제한한다.

| 기업 | 변동성 | 1턴 일별 증감 한계 | 0일차 대비 범위 |
|---|---|---:|---:|
| AI | 높음 | ±8%p | ±50% |
| SPACE | 높음 | ±8%p | ±50% |
| FOOD | 낮음 | ±1.2%p | ±8% |
| BANK | 낮음 | ±0.8%p | ±6% |
| BIO | 극단적 | ±15%p | ±80% |
| AUTO | 중간 | ±3.5%p | ±20% |

일별 폭은 1턴 기준 `1 + 0.05 × (턴-1)`배, 10턴 1.45배이며 기준대비 범위는 유지한다. 수동 설계 fixture는 난수 일별 한계와 다를 수 있다.

### 자산·수익 계산

시작 자산은 10,000 게임머니다. 황금 코인과 별개다. 정보는 코인, 상점·입찰 비용은 게임머니를 사용한다.

```text
S = 재기 지원 반영 후 해당 턴 시작 자산
I = S - 해당 턴 확정 상점·입찰 비용
첫 기업 원금 = trunc(I × 첫 weightBps / 10000)
둘째 기업 원금 = I - 첫 기업 원금
구간 수익률 bps = 청산일 변화율 bps - 진입일 변화율 bps
기업 원본 수익률 = 해당 기업 구간 수익률 합
기업 최종 수익률 = 금융·능력 효과 적용 후 최저 -10000bps로 제한
기업 손익 = trunc(배정 원금 × 기업 최종 수익률 / 10000)
최종 자산 = max(0, I + 두 기업 손익 - 실제 감산 + 효과 수입)
턴 수익률 = (최종 자산 - S) / S
누적 수익률 = (현재 자산 - 게임 시작 자산) / 게임 시작 자산
```

`trunc`는 0방향 버림이다. 원금 101·수익률-150bps의 손익은-1이다. I=10,001·60:40이면 원금 6,000과 4,001로 잔돈을 보존한다. 금액·곱셈 중간값은 C# `long` 등 충분한 정수 범위를 확보한다.

게임 공식은 가격 비율 대신 변화율 차이를 쓴다. AI 10일 -40%→15일 +30%는 구간+70%다. 다른 기업·투자 비중까지 반영한 플레이어 수익률과 구분한다. 누적 수익률은 턴 수익률의 단순 합이 아니다. 구매·입찰 비용도 턴 수익률에 포함한다. 재기 지원은 다음 턴S에 먼저 포함해 그 턴 투자 수익으로 세지 않는다.

### 파산·순위·표시

- 기업 최종 손실률 최저 -100%, 공격 후 자산 최저 0이다.
- 자산 0은 파산 표시만 하고 탈락 없음. 다음 턴 시작 1,000 지원, 순위 자산에 포함. 기본 1턴 fixture에는 없다.
- 턴 중 총자산 동점은 공동순위, 표시 순서만 ID다. 예:1·1·3·4위.
- 최종 동점은 자산→남은코인→최고 단일턴 수익률→시작 공개 추첨 타이브레이크 순번이다.
- B가 총자산·턴 수익률·누적 손익·누적 수익률·추이를 만들고 A가 공개 전달, D가 플레이어별 색상으로 표시한다.
- 현재 턴·순위 확정 여부·다음 이벤트도 표시한다. 역전·최고 수익률 등 알림 연출은 기본 검증 후 추가한다. 공격·능력 알림에는 대상·종류만 넣는다.

## 8. 후속 입찰·아이템·능력의 확정 규칙

기본 시제품 이후 같은 규칙으로 확장하기 위한 내용이다. `inventory: []`, `abilityId: "NONE"` 사례 통과를 아래 기능 완료로 보고하지 않는다.

### 입찰과 성과 보상

| 시점 | 대상 | 지불·배정 |
|---|---|---|
| 3턴 시작 | 블랙박스 분석권 1개 | 비밀 최고가 입찰, 낙찰자만 지불. 모두 0이면 유찰 |
| 6턴 시작 | 프리패스 1개 | 비밀 최고가 입찰, 낙찰자만 지불. 모두 0이면 유찰 |
| 9턴 시작 | 9·10턴 자리 선택 우선순위 | 점수순 선호 자리 배정, 각자 자기 입찰액 지불. 모두 0도 무료 배정 |
| 3·6·9턴 정산 후 | 이번 턴 수익률 1위 | 코인 1개, 공동 1위 전원. 입찰 아이템 중복 지급 없음 |

입찰액 0~`floor(S×10%)`, 정수 1머니 단위, 확정 후 변경 불가, 마감 전 타인 금액 비공개다. 동액은 턴 시작 자산이 낮은 참가자→시작 타이브레이크 순번이다.

프리패스는 9턴 입찰 때 사용 여부를 제출한다. 점수 25% 가산, 실제 지불은 원래 금액, 사용 후 소모다. 정수 비교는 프리패스 `입찰액×125`, 일반 `입찰액×100`이다. 환급·무조건 선점 없음. 입찰 15초 안에 자리 선호를 함께 제출하며 추가 선택 시간을 붙이지 않는다. 10턴 재입찰 없음.

A는 입찰 단계·마감·자리 반영, C는 입찰·프리패스·보상 규칙, B는 확정 비용의 자산 반영, D는 입력·결과를 연결한다. 세부 함수·DTO는 후속 공통 계약으로 맞춘다.

### 상점·아이템

가격은 비율×S를 0방향 버림하되 최소 1게임머니다. S=0·잔액 부족은 구매 불가다. 상점 구매 턴당 1개, 인벤토리 최대 3개, 낙찰·보상 초과분은 그 아이템 대신 코인 1개다.

금융형·정보형·공격형 각각 턴당 1개 사용, 이전 턴 구매품 보관 가능. 유효 사용 확정 시 소모하며 효과 미발생·정치인 방어로 반환하지 않는다. 잘못된 대상·단계·입력은 거절·미소모다. 쿨다운은 능력에만 있다.

| 아이템 | 분류·가격 | 확정 효과 |
|---|---|---|
| 증폭기 | 금융·S의 3% | 본인 선택 기업의 전체 구간 수익률×2. 손실도 적용 |
| 하락 파쇄기 | 금융·4% | 본인 선택 기업의 전체 구간 수익률 부호 반전 |
| 방패/리스크 헤지권 (`SHIELD`) | 금융·2% | 능력 배율 후 -3~+3%는+5%, -3% 미만은 손실 절반, +3% 초과 유지 |
| 대폭발 탐지기 | 금융·5% | 본인 지정 1구간 원본 변화율 차이 절대값≥15%면 기업 수익률+50%p, 미만 보너스 0 |
| 블랙박스 분석권 | 정보·2% | 선택 기업 미열람 1묶음 공개. 대상 없으면 거절 |
| 정보 왜곡 | 공격·2% | 대상 유료 묶음 중 서버 무작위 1개를 10초간 `???` 가림. INFO 종료 시에도 해제. 원본·정산 불변 |
| 정보 훔치기 | 공격·3% | 대상 유료 묶음 중 본인 미열람 1개 서버 무작위 복사 |
| 수익률 감소 | 공격·4% | 턴 시작 자산 상위 2명 중 본인 외 1명, 정산 시 대상 I의 10% 감산. 대상별 성공 턴당 1회 |
| 블랙웨일 프리패스 | 특수·상점 없음 | 6턴 입찰 획득, 9턴 점수 25% 가산 후 소모 |

금융형은 INVESTMENT에서 본인 선택 기업에 지정하고 주문 잠금과 함께 확정한다. 정보형·공격형은 INFO, 프리패스는 9턴 AUCTION이다. 왜곡·훔치기는 유료 정보 없는 대상을 거절하되 구매목록을 공격자에게 미리 보여주지 않는다. 무료·ITEM·STOLEN 정보는 훔치기 대상이 아니다.

### 고유능력

시작 전 각자 무작위 3후보 중 1개 선택, 플레이어 간 중복 허용, 미선택 첫 후보다.

| 능력 | 확정 효과 |
|---|---|
| 정치인 | 사용 가능 상태의 첫 공격형 아이템 또는 기업사냥꾼 감산 자동 방어. t턴 발동 후t+3턴 시작 재사용. 성공 시 공격 아이템 3종 중 무작위 1개, 정원 초과 코인 1개 |
| 작전 세력 | 훔치기 1개로 시작. 수익률 감소 실제 차감액 25% 획득. 훔치기 성공 시 다음 턴 첫 정보 1묶음 무료 |
| 정보상 | 매 턴 첫 구매 1묶음 무료. 블랙박스는 같은 기업 미열람 묶음을 선택 순서대로 최대 2개 공개 |
| 기업사냥꾼 | 하락 파쇄기로 원본 하락 기업에서 양의 수익이면, 공동 투자에서 양의 손익을 낸 상대 1명의 손익을 감산. 기준은 대상 상대가 그 기업에 배정한 원금의 5%. 대상은 이익 최대→추첨순번. 남은 양의 기업손익 한도, 차감액 50% 획득. 적격자 없으면 추가효과 없음 |
| 도박사 | AI·SPACE·BIO 손익률×1.2, 증폭기 결합 2.4배, 대폭발 성공+60%p. 실패 시에도 기본 손실배율 유지 |

정치인의 방패 사용은 재사용 가능 턴을 1 줄이되 현재 턴 이전으로 당기지 않는다. INFO 공격 방어는 유효 요청 때 기록하며 나중 방패로 소급 변경하지 않는다. 기업사냥꾼 방어는 정산 시 상태로 판정한다. 무료 능력권은 이미 열람한 묶음에 소비하지 않고 다음 턴으로 누적하지 않는다.

열람 출처는 `PUBLIC`, `PURCHASED`, `ABILITY`, `ITEM`, `STOLEN`으로 구분한다. 실제 코인을 지불한 `PURCHASED`만 유료 정보 공격 대상이다.

### 효과·정산 적용 순서

1. 시작 지원·코인 지급 후 S 고정 → 입찰·상점 비용 → I 산출.
2. 기업 원본 구간 수익률 합 → 하락 파쇄기 반전 → 도박사×1.2.
3. 증폭기 또는 방패 또는 대폭발 보너스. 금융형 턴당 1개라 여러 금융형 중첩 없음.
4. 기업 수익률 -100% 하한 후 원금·정수 손익 계산.
5. 정치인 방어를 반영해 수익률 감소·기업사냥꾼 감산. 대상 감산 합 I의 15% 이하, 자산 0 이상.
6. 실제 차감액에만 작전 세력 25%·기업사냥꾼 50% 보상을 마지막에 일괄 지급. 연쇄 배율·감산 없음.
7. 자산·성과·순위 확정 후 3·6·9턴 성과 코인 지급.

감산은 유효 요청 기록 순서다. 기업사냥꾼 대상은 금융효과 후·공격 전 양의 손익 스냅샷으로 정하고 여러 사냥꾼은 시작 추첨순번으로 처리한다. 이미 차감한 금액·15% 상한·남은 양의 기업손익·자산을 고려한다. 방어된 감산은 차감 0·공격자 보상 0이다.

C는 효과 사용·대상·방어 기록, B는 이 순서의 정산, A는 문맥·실행 시점, D는 허용된 결과 표시를 담당한다. 같은 효과를 C와 B에서 중복 적용하지 않는다.

## 9. 통신·공개 범위·연결 정책

| 데이터 | 전달 대상 |
|---|---|
| 참가자·단계·차례·기업별 잔석 | 전체 |
| 기업별 무료 2묶음 | 전원 동일 |
| 구매 정보·코인·본인 주문 | 해당 본인만 |
| 전체 시장·전체 구매 원장·전체 주문 | 서버 내부 |
| 총자산·성과·순위·추이 | 전체, 타인 투자 내역 제외 |

차례·잔석으로 선택을 추론할 수 있으므로 완전 익명이라고 설명하지 않는다. 전체 시장 공개는 전원 주문 잠금 뒤 A가 전환한다. 공개 전 원본을 보내 UI에서 가리는 방식은 쓰지 않는다. 방장PC 에 원본이 있으므로 정상 화면 정보 제한과 변조 호스트 보호는 구분한다.

- `senderPlayerId`는 A가 접속 정보로 결정한다. 클라이언트의 신원·잔액·시세 주장을 확정값으로 쓰지 않는다.
- 방의 변경 요청을 순서대로 처리한다. 코인 1개에 동시 구매 2개 또는 잔석 1개에 동시 선택 2개가 모두 성공하지 않게 한다.
- 캐시 키는 방·플레이어·턴·`requestId`, 방 종료까지 유지. 같은 내용은 원응답, 다른 내용은 `REQUEST_ID_CONFLICT`다.
- 새 요청은 참가자·턴당 256개까지, 초과 `RATE_LIMITED`. UI도 구매중 재클릭·무한조회 제한.
- 지급·비용·자동 행동·잠금·정산은 중복 적용 방지, 실패 시 일부 상태만 변경 금지.
- 호스트 이탈은 종료 안내, 호스트 이전·영구 복구 없음.
- 일반 참가자는 개인 토큰으로 30초 내 재접속. 시계는 계속 진행하고 부재 중 자동 행동. 30초 후에도 슬롯을 유지하고 해당 판은 자동 진행한다.

공통 오류는 구매 `NOT_ENOUGH_COINS`, `ALREADY_VISIBLE`, `INVALID_BUNDLE`, `INVALID_COMPANY`, `WRONG_PHASE`, `STALE_TURN`, 선택 `COMPANY_FULL`, `DUPLICATE_COMPANY`, `NOT_YOUR_TURN`, 주문 `INVALID_HOLDING_DAYS`, `TOO_MANY_INTERVALS`, `OVERLAPPING_INTERVALS`, `INVALID_RATIO`, `INVALID_DAY`, `COMPANY_NOT_SELECTED`, `MISSING_INTERVAL` 등을 사용한다. 검사 우선순위·응답은 공통 계약·기대 사례에 맞춘다.

## 10. 개발 자료·임시 데이터 사용법

### 저장소에 포함할 자료

독립 검증을 위해 원본 JSON·생성/검증 스크립트, 공통·역할 자료, 패키지 검사가 참조하는 기획 원본을 함께 관리한다. 다음은 같은 저장소에 Unity와 자료를 두는 예시이며 실제 프로젝트 위치·버전·패키지는 먼저 확인한다.

```text
저장소/
├─ Assets/ · Packages/ · ProjectSettings/   Unity를 이 위치에 둘 경우
├─ 7주차 발표정리/                         PPTX·정리 Markdown
├─ 요구사항명세서/
└─ 개발 정리/
   ├─ 참고사항/전체 프로세스 정리.md          이 문서
   ├─ 임시 데이터 및 검증용/                 원본 JSON16개·Python 스크립트

      ├─ README.md · 공통 문서4개
      ├─ build_packages.py · source_snapshot.json
      └─ A/ · B/ · C/ · D/                작업지침·임시데이터·통과기준
```

전체 시장·타인 원장·정답은 개발용이다. 일반 클라이언트 Resources·StreamingAssets나 배포 빌드에 통째로 넣지 않는다.

### 역할별 입력과 기대 결과

| 담당 | 핵심 입력 | 비교할 결과 |
|---|---|---|
| [A](../AI%20개발%20가이드/A/작업지침.md) | 방 초기 상태·선택 replay·요청·관련 사례 | 차례·잔석·개인 응답·중복 방지 |

개발자는 자기 `임시데이터.json`을 실제 구현에 입력하고 `통과기준.json`과 비교한다. 공통 원본에서 추출한 자료이므로 같은 사례를 원본으로 전부 다시 검사할 필요는 없다. 역할별 `integrationChecks`는 실제 C#/Unity/통신에서 추가 확인한다.

## 11. 독립 개발부터 실제 4인 통합까지

1. **저장소 확인:** Unity 세부 버전·패키지·Shared·기존 변경을 확인한다. 계약이 없으면 A가 제안하고 B/C/D가 사용 관점에서 검토한다.
2. **공통 계약 dev 선병합:** 필드·enum·단위·오류·이벤트·서비스를 하나로 정하고 복제 DTO를 만들지 않는다.
3. **독립 구현:** B는 순수 선택·주문·정산, C는 임시 시장으로 구매·개인뷰, D는 같은 계약의 Mock UI, A는 Mock B/C로 신원·차례·라우팅을 검증한다.
4. **실제 규칙 로컬 연결:** A의 Mock을 실제 B/C로 바꾸고 고정 입력 결과를 비교한다. D 입출력은 유지한다.
5. **네트워크 연결:** D 공급자를 실제 A 서비스로 교체한다. 로컬 멀티 인스턴스·실제PC 4대에서 호스트 포함 수신 범위를 확인한다. 로컬과 인터넷 검증을 구분한다.
6. **실제 진행 확장:** 고정 1턴 뒤 실제 시계·자동 행동·복수턴·순환·난수 시장을 검증한다. 후속 효과는 사례를 추가하며 연결한다.

Mock도 잔액·열람 상태와 실패·지연을 재현해야 한다. 모드별 초기 상태를 분리하고 Mock 실행을 실제 통신 완료로 보고하지 않는다. UI 재작성 대신 같은 서비스의 공급자 교체를 목표로 한다.

### 기본 1턴 공동 실행

전원 자산 10,000·코인 3으로 시작한다. P1은 AI 묶음 1을 구매해 코인 2, P2는 변화 없음. 이후 다음 선택을 재생한다.

| 번호 | 참가자 | 기업 |
|---|---|---|
| 1 | P1 | AI |
| 2 | P2 | SPACE |
| 3 | P3 | BIO |
| 4 | P4 | AI |
| 5 | P4 | BIO |
| 6 | P3 | AUTO |
| 7 | P2 | BANK |
| 8 | P1 | FOOD |

완료 시 AI·BIO 잔석 0, 나머지 1, INVESTMENT로 전환한다. 각 연결에서 본인 주문을 제출하고 잠금·공개·정산한다.

| 참가자 | 기업·비중·구간 | 기업별 손익 | 최종 자산 | 턴 수익률 |
|---|---|---|---:|---:|
| P1 | AI 60% 10→15 / FOOD 40% 5→10 | +4,200 / +80 | 14,280 | +42.8% |
| P2 | SPACE 70% 5→10 / BANK 30% 5→10 | +1,050 / +30 | 11,080 | +10.8% |
| P3 | BIO 50% 5→10 / AUTO 50% 5→10 | -1,500 / +400 | 8,900 | -11% |
| P4 | AI 50% 10→15·20→25 / BIO 50% 15→20 | +4,250 / -1,500 | 12,750 | +27.5% |

P4 AI는 70%+15%=85%를 같은 원금 5,000에 적용한다. 공개 순위는 **P1→P4→P2→P3**다. 비용·효과 없는 1턴이라 턴·누적 수익률이 같다. 전광판에는 타인 기업·금액·구간을 넣지 않는다.

## 12. 검증·갱신·완료 기준

### 개발자와 관리자 검증

| 검증 | 개발자 | 관리자 | 확인하는 것 |
|---|---|---|---|
| 역할 입력→실제 구현→기대값 | PR 전 실행·기록 | 리뷰·필요시 재실행 | 실제 담당 기능 결과 |
| 원본 fixture·역할 패키지 검사 | PR 전 실행 | 검토·dev 통합 후 실행 | 자료 일관성·추출본·출처·링크 |
| Unity 로컬·UI 연결 | 변경 기능 실행 | dev 공동 흐름 확인 | 요청→규칙→화면 연결 |
| 실제 4인·타이머·장애·재접속 | 관련 담당 공동 실행 | 통합 결과 확인 | 실제 수신·진행·연결 정책 |

저장소 루트에서 실행한다. Python 표준 라이브러리만 사용하며 Unity 설치 없이 자료를 검사한다.

```powershell
python "개발 정리/임시 데이터 및 검증용/validate_fixtures.py"
python "개발 정리/AI 개발 가이드/build_packages.py" --check
```

첫 명령은 JSON·단위·6기업·31날짜·34참조 사례·8회 선택·정산·P1/P2 분리, 둘째는 추출본·사례 배정·출처 스냅샷·문서 링크를 확인한다. **이 명령은 팀의 C# 구현이나 Unity 네트워크를 실행하지 않는다.**

실제 구현에서는 음수 버림·잔돈·공동순위·다중턴 누적, 조회 실패 무변경·동시 구매·배열 불변성, 호스트 개인뷰·재전송·늦은 응답, 주문 잠금·정산 중복도 확인한다. 실제 마감·자동 행동·효과·연결 장애는 별도 실행 기록을 남긴다.

### 의도적인 원본 변경과 갱신

기획 변경은 확정 기록·공통/역할 문서·생성/검증 코드·기대값의 영향을 검토한다. 정산 정답은 근거를 남기고 독립 재계산한다. 구현을 통과시키려고 기대값부터 바꾸지 않는다.

원본 fixture를 변경하려면 생성기에 먼저 반영한 뒤 실행한다. 원본 JSON 16개를 덮어쓴다.

```powershell
python "개발 정리/임시 데이터 및 검증용/generate_fixtures.py"
python "개발 정리/임시 데이터 및 검증용/validate_fixtures.py"
```

기획·개발 프로세스·fixture 변경을 검토·반영한 뒤 역할 패키지와 출처 스냅샷을 갱신한다.

```powershell
python "개발 정리/AI 개발 가이드/build_packages.py" --write
python "개발 정리/AI 개발 가이드/build_packages.py" --check
```

`--write`는 역할 JSON 8개·`source_snapshot.json`을 덮어쓰고 Markdown은 고치지 않는다. 일반 PR·통합 검사는 `--check`다. 매 통합마다 `--write`로 경고를 지우지 않는다. 정답에 PASS를 쓰는 대신 PR·별도 기록에 실측값을 남긴다.

```text
        → dev 통합 실행 → 관리자가 dev → main PR → 안정 버전
```

관리자는 저장소·dev·권한·병합을 관리한다. 개발자는 완료 기능을 **자신의 브랜치에서 dev로 직접 PR**을 보낸다. main은 검증된 발표·배포 버전이다. 기능을 dev에 직접 push해 합치지 않고 PR로 검토한다.

작업이 저장됐고 origin/dev가 있는 경우의 예시다. 기존 변경을 확인하고 다른 사람의 작업을 지우지 않는다.

```powershell
git status
git switch dev
git pull --ff-only origin dev
git switch -c feat/23-info-purchase
```

구현·검증 후 관련 파일과 새 에셋의 `.meta`만 골라 커밋·푸시한다. PR은 **base: dev / compare: 본인 기능 브랜치**다. 다른 PR이 먼저 병합되면 저장된 본인 기능 브랜치에서 최신 dev를 합치고 검증을 다시 한다.

```powershell
git fetch origin
git merge origin/dev
```

공통 구매 DTO·서비스→C 규칙과 D Mock UI 각각→A 실제 통신 순으로 계약을 먼저 dev에 합친다. 선행 PR이 미병합이면 번호를 적고 Draft로 공유한다. 상세 절차는 [GitHub 병합 지침](../AI%20개발%20가이드/03_GitHub_병합_지침.md)을 따른다.

### AI 전달·PR 기록

매 작업마다 공통 4문서와 자기 폴더의 `작업지침.md`, `임시데이터.json`, `통과기준.json`을 읽힌다. 최신 Shared, Issue·완료 조건, 기준 dev 커밋·기존 변경도 제공한다. 예전 대화로 현재 계약을 추측하지 않게 한다.

```text
나는 [A/B/C/D] 담당이다.
공통4문서·내 역할3파일·최신 Shared를 읽어라.
기준은 dev의 [커밋], 작업은 [Issue·완료 조건]이다.
Unity 버전·패키지·기존 변경을 먼저 확인해라.
내 담당 상태를 구현하고 DTO·규칙을 임의 복제하지 마라.
역할 입력을 실제 구현에 넣어 기대값과 비교하고 미실행 검증을 구분해라.
최신 dev에서 만든 기능 브랜치로 작업하고 PR 대상은 dev로 해라.
커밋·푸시·PR은 이번 허용 범위만, 병합은 담당자에게 맡겨라.
```

PR에는 동작·Issue·요구사항·Case ID, 계약 변경·선행 PR, 입력→실측→기대값, 모드·Mock 여부, C#/Unity/실제 4인 검증·미실행 항목, Scene·Prefab·`.meta`, 다음 연결 담당자를 적는다.

Unity는 정확한 에디터·패키지 버전을 맞춘다. Assets·Packages·ProjectSettings 관리, Library·Temp·Logs 등 생성 폴더·자격 증명 제외. 공통 Scene 동시 편집을 조율하고 화면은 Prefab으로 분리한다. `.meta` GUID를 보존하고 충돌 후 Missing Script·참조·버튼을 Unity에서 확인한다. 공유 브랜치 force push·타인 변경 일괄 덮어쓰기로 해결하지 않는다.

## 14. 2주 일정·공동 점검

작업 시작일 기준 상대 일정이며 확정 날짜·완료 현황이 아니다.

|---|---|---|---|---|---|

회의에서는 추가 기능의 실제 동작·오류·의존성·계약 변경·병합 순서를 확인한다. 회의 시간·발표 후 논의 운영은 [팀장이 정리해본 전체 흐름](./팀장이%20정리해본%20전체%20흐름.md)를 함께 본다.

### 기능·통합 완료 체크리스트

- [ ] 최신 rules-v2·계약·역할 자료·실제 저장소를 확인했다.
- [ ] 동일 상태의 이중 관리·DTO/규칙 복제가 없다.
- [ ] 역할 입력으로 실제 구현과 기대값을 비교했다.
- [ ] 실패 무변경·중복 방지·동시 요청을 확인했다.
- [ ] 방장도 같은 경로이며 P1 구매가 P2에 새지 않는다.
- [ ] 잠금 뒤 시장 공개, 정산 자산 적용은 턴당 1회다.
- [ ] 실제 타이머·자동 행동과 수동 모드를 구분했다.
- [ ] fixture·역할 패키지 검사를 통과했다.
- [ ] 실제 4인·인터넷·재접속·효과의 실행/미실행 범위를 적었다.
- [ ] Scene·Prefab·`.meta` 참조와 최신 dev 반영을 확인했다.
- [ ] 기능 PR은 dev 대상이며 관리자/지정 담당자가 병합한다.

매일 최신 dev에서 구매→선택→주문→공개→정산을 가능한 범위까지 확인하고 미연결 구간을 기록한다. main은 통합 검증한 결과를 기준으로 반영한다.
